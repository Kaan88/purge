# Purge engine research notes (2026-11-11)

This file holds the raw findings of the eight research tracks and four plan reviews behind `ENGINE_PLAN.md`. The plan is the decision document: where they differ, the plan wins.

## bcu-junk

BCU's junk engine (UninstallTools\Junk, about 3.2k lines) runs 22 scanners found by reflection, one after another, with no parallelism. Each scanner re-walks its locations for every target app. The confidence model adds up integers (ConfidenceRecords.cs) and maps the sum to four levels: below 0 Bad, 0–1 Questionable, 2–4 Good, 5 or more VeryGood. The GUI preselects Good and above. That means one +4 "ExplicitConnection" is enough to preselect an item, and so is an exact name match at depth 0. Duplicates are merged only when two items have the same display string, so a parent folder and its children both stay on the delete list. The BCU-console crash in the VM is explained exactly by this. InstallLocationScanner yields `C:\Program Files\Mozilla Firefox`, UninstallerLocationScanner yields `...\uninstall`, and SpecificUninstallerKindScanner (NSIS) yields `...\uninstall\helper.exe`. Program.cs:384 deletes them in scanner order with no try/catch. The VB `FileSystem.DeleteFile` call then throws FileNotFoundException, Main's catch (Program.cs:153) aborts the whole batch, and nothing was backed up. A worse bug affects the COM scanner. `UninstallToolsGlobalConfig.IsSystemDirectory(string)` returns true for any path that doesn't exist, because .NET returns (FileAttributes)-1 for missing paths (I checked this on the host with .NET 10). `ComScanner.FindJunk` exits early when the install folder is gone (ComScanner.cs:39), and `Setup` drops every CLSID whose DLL is gone (ComScanner.cs:203). So after a real uninstall, COM leftovers are almost never found. The VM logs match: the 7-Zip dry run (before uninstall) listed its CLSIDs, and the real post-uninstall run reported "No remaining junk". BCU has no scanner for ProgIDs, file associations or shell verbs. It checks OpenWithProgids only against COM ProgIDs, and has nothing for App Paths, PATH, sparse MSIX packages, shell-extension handler keys outside `.ext\ShellEx`, per-machine MSI UserData (S-1-5-18), UpgradeCodes or SharedDLLs. That accounts for every miss measured on VS Code, Python and Git. The console also passes the target apps as the full app list (`FindJunk(apps, apps, ...)`), which turns off every "used by another app" safety check. The registry value backup writes broken .reg files: value names are not escaped, the file is UTF-8 instead of UTF-16, and only string values are backed up, the rest silently. The Rust port should keep BCU's knowledge of which locations to scan and its explicit-path matchers. It should replace the additive score with a typed evidence and blocker model and add a scan of the app's registrations taken before the vendor uninstaller runs. Deletion should be planned as a transaction that removes nested items, goes deepest-first, backs up, re-checks each item just before deleting it, and treats an already-missing item as done. The AI agent can only add capped evidence or unverified hypotheses on top of the same deterministic checks.

### Recommendations

- Do not port BCU's additive integer scores. Port its locations and explicit-path matchers into a typed Evidence/Blocker model. Auto-preselect only items with at least one explicit fact (points into the install folder, appears in the pre-uninstall reference snapshot, verified MSI record, uninstaller artifact, install trace) and no blockers. Anything matched by name alone goes to Review, unchecked.
- Capture a fingerprint before running the vendor uninstaller: install folder, executables, MSI codes, and a snapshot of every registry key or value that references the install folder or the app's ProgIDs, with their parent keys. After the uninstall, an 'emptied by uninstall' rule removes those keys. This alone covers the measured VS Code (135 keys), Python (.py* and Python.* ProgIDs) and Git (LibraryFolder\Background\shell, sh_auto_file) misses that every tool failed on.
- Rewrite the COM scanner rather than porting it. BCU's IsSystemDirectory(string) returns true for any missing path (.NET gives Attributes = -1), so ComScanner exits once the install folder is gone (ComScanner.cs:39) and skips CLSIDs whose DLL is deleted (:203). Add LocalServer32, AppID, all TypeLib versions and LCIDs, and every shellex handler location plus Shell Extensions\Approved.
- Build the deletion engine as a transaction: remove nested candidates, delete deepest-first in a fixed order (services, tasks, API unregistration, registry values, keys, files, folders, empty parents), re-check existence and fingerprint just before each delete, treat 'already gone' as success, never abort the batch, back up to an in-process journal (correct UTF-16 .reg with escaped names and every value type, files moved to a per-volume backup folder), and use MoveFileEx delay-until-reboot for locked files.
- Add new scanners for the measured gaps: ProgID, file-association and shell-verb scanner; sparse AppX packages through PackageManager plus EffectiveExternalPath; App Paths; PATH segments; SharedDLLs; MSI UserData\S-1-5-18 and UpgradeCodes, gated on MsiQueryProductState; firewall through the INetFwPolicy2 API including the AppIso stores; and per-user scanning across HKU\<SID> and ProfileList, so elevation under another admin account doesn't scan the wrong profile.
- Replace name matching with a token-aware matcher: keep symbol suffixes such as notepad++, use stopwords, and draw aliases from MSI ProductName, Inno AppId, NSIS key, exe names, publisher and URLInfoAbout host. Add vendor-parent pruning (EmptyAfterPlan) and data-driven knowledge packs, e.g. Mozilla-<guid> and mozilla.org, to reach Firefox's missed leftovers.
- Build a deny-list that covers ancestors as well as exact paths: every KNOWNFOLDERID for each profile, Program Files roots, WindowsApps, Package Cache, every other app's install folder in both directions, and registry roots such as Software\Policies, the Classes\*\shell and shellex roots, and system CLSIDs. Fix every raw StartsWith/Contains path compare to be separator-aware.
- Build one index of the file system and registry per run and match all targets against it. BCU re-walks AppData, Program Files and the 8 Software roots for every target and scanner.
- Upgrade the VM benchmark. Replace score.ps1's ambient regex, which hides real Classes\Interface and Installer\Dependencies leftovers, with a measured idle-churn baseline. Report precision and per-scanner attribution. Score the engine's JSON plan directly. Add test cases: two Pythons, same-vendor apps, short names, Notepad++ vs Notepad, a user-scope install, sparse MSIX, a firewall rule or service, and elevation as another admin account.
- Shape the AI-agent interface as: read the Plan as JSON; write capped Ai evidence (can always demote, can never clear a blocker or reach auto-preselect alone); add Hypothesis candidates that go through the same checks and start unchecked; propose knowledge-pack and deny-list rules that are adopted only after the VM benchmark shows a recall gain with zero danger.

### Open questions

- Which app owns the 7-Zip truth leftover `HKLM\SOFTWARE\Classes\CLSID\{042D2B7D-308B-4032-A569-466A8E0DE728}`? MSI removed 7-Zip's own {23170F69-...} CLSIDs. Its InprocServer32 or LocalServer32 should be read in the VM before this item is counted as a 7-Zip leftover.
- Will Purge always run elevated as the same account as the logged-on user? If over-the-shoulder elevation with a different admin account is possible, HKCU and AppData must be resolved through HKU\<SID> and ProfileList. That decides the per-user scanning design.
- How should UCPD-protected UserChoice keys and Windows-shipped `HKCR\.ext` defaults be handled? Proposal: never touch them. That requires a baseline list of Windows-shipped extension keys, which could be captured from the clean VM snapshot.
- Does `Package.EffectiveExternalPath` reliably return the external location for sparse packages (VS Code, Notepad++)? I could not find a doc that confirms it. Needs a quick check in the VM; the fallback is matching the AppxManifest external-content properties, or publisher and name, against the Win32 entry.
- Is the Recycle Bin acceptable as the file backup at all, or should Purge always use its own per-volume journal folder? Recommendation: always use the journal, because the Recycle Bin silently deletes permanently on volumes without one.

## locations

Purge's cleaner should decide what is a leftover from an evidence graph built around each app, not from name matching. The anchors are the install folder, exe names, ProgIDs, CLSIDs, AppUserModelIDs (AUMIDs), the AppX package family, MSI product/component codes and service/task names. The engine follows every reference that points at those anchors and checks each candidate against a protection index: other installed apps' reverse index, the Windows baseline taken from the VM snap-*-0.json files, and an MSI ownership index built from every installed product's cached .msi tables. Re-reading the VM data changed two conclusions. (1) Python's .pyc/.pyd/.pyo/.pyw/.pyz/.pyzw keys, the Python.* ProgIDs, CLSID {BEA218D2...} and HKLM\SOFTWARE\WOW6432Node\Python belong to the "Python Launcher" MSI {73831AC2...}, which the vendor uninstall left installed (python-result.json entries_left). Removing them would be a false positive; they are protected and the UI should offer to uninstall the launcher. (2) VS Code's 135 extension leftovers are 105 whole `.ext` keys plus 30 `OpenWithProgids` subkeys under extensions that already existed. Inno's `uninsdeletevalue` removed the `VSCode.<ext>` values but, without `uninsdeletekeyifempty`, left empty key skeletons. They are only reliably attributable through a journal Purge captures before uninstalling (or a tracer). Without one they fall into an unattributed "empty skeleton" category that is harmless to remove but never shown as app-owned. Git's leftovers have the same cause: its uninstaller deletes only git_shell/git_gui and leaves the parent shell key; sh_auto_file is written with ifempty flags that do not clear the parent keys. Several locations must only ever be removed through their owning API, never by deleting registry keys: AppX/sparse packages (PackageManager plus Deprovision), scheduled tasks (Task Scheduler COM), firewall rules (rule ID = registry value name, removed through NetSecurity/INetFwPolicy2), services, Defender exclusions (Remove-MpPreference), certificates and fonts. Some locations are report-only: UserChoice (hash plus the UCPD driver), StateRepository, AppxAllUserStore, TaskCache, BAM, Winsock catalog and the driver store. The benchmark needs value-level snapshots and an "owned by a still-installed product" label, and its blanket `Interface\{...}` ambient filter hides real Firefox COM leftovers.

### Recommendations

- Make the evidence graph plus protection index the core of the engine: anchors (install dir, exe set, ProgIDs, CLSIDs, AUMIDs, package family, MSI product/components, services, tasks) are collected before uninstall. Every Finding carries positive and counter evidence. HARD counters (Windows baseline, system paths, owned by an installed MSI, referenced by another app, AppX/Windows-managed) block actions regardless of score.
- Add a pre-uninstall journal step. Snapshot the app's anchors, its MSI tables (from the cached .msi) or its Inno unins000.dat, and the state of every Classes\.<ext>\OpenWithProgids holding one of its ProgIDs. After the vendor uninstaller, items that became empty or dangling get UninstallJournal evidence. This is the only reliable way to clean VS Code's 135 extension skeletons and Git's shell/sh_auto_file residue.
- Build an MSI ownership index from all installed products' cached databases (Registry/ProgId/Extension/Class/TypeLib/File/Shortcut/ServiceInstall tables) in the background after launch. Use it to protect items such as Python's .pyc/.pyd/Python.* keys (owned by the still-installed Python Launcher {73831AC2...}) and to suggest related products to uninstall.
- Remove AppX/sparse packages (VS Code, Notepad++), scheduled tasks, firewall rules, services, Defender exclusions, certificates and fonts only through their APIs (PackageManager + Deprovision, ITaskService, NetSecurity by rule ID, SCM, Remove-MpPreference, CertStore). Never edit StateRepository, AppxAllUserStore, TaskCache or UserChoice. Report UserChoice instead (hash plus UCPD).
- Port these BCU scanners with attribution: SoftwareRegKey, CommonDrive, Com, AppCompat, EventLog, FirewallRule, InstallerFolders, RegisteredApplications, Tracing, HeapLeak, AudioPolicy, UserAssist, Prefetch, WER, Shortcut, Startup, and the confidence model. Extend Com with LocalServer32, .NET CodeBase and surrogate AppIDs. Add new scanners for ProgID/OpenWithProgids/OpenWithList, shell verbs, App Paths, Applications\<exe>, URL protocols, PATH/env segments, SharedDLLs (dangling only), Package Cache/Burn dependency providers, Active Setup, NativeMessagingHosts, notifications, StartupApproved and other users' hives.
- Make name matching token-aware (keep '++', '#'; no truncation). Resolve shortcut targets instead of matching names. Treat vendor containers (Firefox→Mozilla) as attributable only when no other app of that publisher remains. Keep vendor aliases as a catalog the AI agent can extend under human approval.
- Separate categories: UserData (profiles, dotfolders, Documents) never preselected. 'System tidy' (unattributed empty key skeletons) off by default. Report-only for MSI live registrations, Windows Installer cache, drivers/filters, certificates and Winsock/print providers.
- Upgrade the VM benchmark. Capture value-level data for association/env/run/firewall/SharedDLLs roots plus AppX/task/service/firewall lists. Label 'owned by still-installed product' as must-keep truth. Replace the regex ambient filter (especially the blanket Classes\Interface rule that hides Firefox COM leftovers) with measured null-install churn. Add forced-removal, launched-once, second-profile and same-vendor scenarios. Require 100% precision on preselected items.
- Expose the AI hook as data-only: the agent can re-rank, add bounded 'ai' evidence (at most ±2), request scanner expansions and propose catalog rules. It cannot bypass HARD counters or execute deletes; every action keeps preconditions re-checked at execution time and a captured inverse for restore.

- What do the 105 VS Code `.ext` skeleton keys contain after uninstall: only an empty OpenWithProgids, or any values? The snapshots hold key paths only, so this needs a value-level re-run.
- Can RegLoadAppKey be used safely to read unloaded NTUSER.DAT/UsrClass.dat hives of other users without SeBackup/SeRestore, and does mounting interfere with a concurrent logon? Verify before v2 multi-user support.

## evidence

Research only; no project files were changed. The strongest ownership evidence is the installer's own record of what it installed: Inno Setup's unins000.dat, the MSI tables in the cached package, the Burn chain and its dependency keys, and AppX manifests. The vendor uninstaller deletes or changes most of these, so the engine must read them BEFORE it runs the uninstaller. The pipeline is: harvest, then observe the uninstall, then check what is left.

I wrote a read-only unins000.dat parser from the Inno source and ran it on this host. Git's log has 10,504 records and names HKLM\Software\Classes\sh_auto_file and its subkeys. That is the exact Git leftover in the VM: Inno only logs delete-if-empty for the leaf keys, so the empty middle keys stay behind. VS Code's code.iss marks every `.<ext>\OpenWithProgids` entry `uninsdeletevalue`, which explains all 135 empty keys left after uninstall. WinMerge keeps its data under the vendor key "Thingamahoochie", which name matching can never find.

Checking ownership also corrects two benchmark labels. Python's .pyc/.pyd/Python.* keys and the {BEA218D2} drop handler belong to the Python Launcher MSI, which is still installed: the Burn bundle marks it Permanent="yes", so these keys are not orphans. 7-Zip's one "real leftover" CLSID {042D2B7D...} is Windows Defender's SecurityHealthAgent.dll, not anything from 7-Zip.

Next by value come three more sources. First, a path-reference index that finds registry values whose target is in the app's folder (including broken references after uninstall). Second, an ETW trace of the vendor uninstaller's process tree, which is always possible because Purge launches it. Third, publisher and signer names (Firefox → Mozilla), with very large vendors like Microsoft excluded.

Supporting evidence: the USN journal (32 MB max / 8 MB allocation delta on this host, no process information, recent installs only), registry LastWriteTime and file creation-time windows, and Prefetch/Amcache. Safety comes from vetoes: TrustedInstaller ownership, presence in a clean-Windows baseline, MsiEnumClients or SharedDLLs showing another product uses it, or another installed app claiming it.

The proposed evidence graph has typed nodes and edges, each with provenance and a weight. It scores two separate axes: how likely the item is the app's, and how much harm deleting it would do. Any veto blocks deletion. A future AI agent can only request read-only probes that the engine runs, add capped hypotheses, and add vetoes; it can never delete on its own.

### Recommendations

- Make the engine run in three phases (harvest, observe, verify) and always harvest installer manifests, identity and app roots BEFORE launching the vendor uninstaller; most evidence is deleted by the uninstall.
- Build the Inno unins000.dat parser first: the format is fully specified in issrc Setup.UninstallLog.pas, and a 60-line prototype already parses Git, WinMerge and UniGetUI on this host. Add an 'empty skeleton' rule: a key named in the log whose subtree now has zero values is removable. This fixes Git's sh_auto_file and VS Code's 135 OpenWithProgids keys.
- Build the MSI collector: read the cached package read-only via MsiGetProductInfoEx(INSTALLPROPERTY_LOCALPACKAGE) and query the Component/File/Registry/Class/ProgId/Extension/Shortcut/ServiceInstall tables. Use MsiEnumClientsEx, SharedDLLs and Installer\Folders as share vetoes, and flag custom actions as opaque.
- Build the Burn collector (BundleProviderKey, Installer\Dependencies\*\Dependents, BurnManifest.xml Permanent flags) so that leftovers owned by a still-installed permanent package (Python Launcher) are shown as 'uninstall related product too', not as orphans.
- Build a background path-reference index (COM, ProgId commands, App Paths, Run keys, services, tasks, firewall rules, shortcuts, AppCompat) with live and broken-target edges. Port BCU's ComScanner, FirewallRuleScanner, AppCompatFlagScanner, RegisteredApplicationsFinder and ShortcutJunk with Apache-2.0 attribution.
- Run an on-demand elevated ETW helper (Kernel-Process 0x50, Kernel-File 0x1C90, Kernel-Registry 0x7300) during every vendor uninstall and every opt-in Install & trace. Filter by process tree on the consumer side, attribute broker processes within the time window, count EventsLost, and use USN NextUsn bracketing as a lossless backstop.
- Add vendor alias resolution from Uninstall Publisher, the Authenticode signer (CryptQueryObject/CMSG_SIGNER_INFO_PARAM) and VersionInfo CompanyName. Use symbol-preserving tokenization (Notepad++ never equals Notepad) and a mega-vendor list that downgrades vendor-only matches.
- Apply hard vetoes: TrustedInstaller owner or ACL, presence in a clean-OS baseline built from the VM snapshots, System32 or Microsoft-signed reference targets, Inno ExistedBeforeInstall, MSI shared components, and claims by other installed apps.
- Score two axes: ownership (summed typed edges with provenance) and harm (empty / cache / config / user data). Pre-check only items with high ownership and low harm; user-data folders like Firefox profiles stay unchecked with a label even when owned.
- Expose the graph through read, probe and propose APIs for the future AI agent. Agent hypotheses are capped (never Safe on their own), agent vetoes take effect immediately, agent-authored rule packs start at +4 and are promoted only after the VM benchmark shows zero danger, and the agent never deletes.
- Fix the benchmark labels: the 7-Zip CLSID {042D2B7D...} is Defender's SecurityHealthAgent (ambient), and Python's .py* class keys belong to the still-installed Python Launcher. Add WinMerge (vendor key 'Thingamahoochie'), plain NSIS, Squirrel, InstallShield and MSIX apps to the rig, and make zero danger at the Safe band a CI gate.
- Record a (time, NextUsn, JournalID) calibration point on every Purge launch (one unelevated ioctl). Offer enlarging the USN journal only as an explicit opt-in system change.
- Defer NSIS script decompilation (official 7-Zip removed it in 15.06; the code is LGPL and opcodes vary by version) to a later, agent-assisted phase. For NSIS rely on ETW observation, path references and vendor aliases, plus Mozilla's uninstall.log as a vendor-specific parser.

## ui-stack

Recommendation: build the UI in C# (.NET 10) on WinUI 3, using Windows App SDK 2.6.5 (the current stable release). Ship it unpackaged, with the Windows App SDK self-contained and Native AOT, and reference only the WinUI and Runtime component packages. Put the Rust engine in a separate engine.exe that speaks newline-delimited JSON-RPC 2.0. The UI talks to an unelevated engine over stdio. When elevation is needed, the same binary starts as an elevated broker over an ACL-locked named pipe. A third mode serves MCP over stdio for a future AI agent. The UI runs asInvoker, not requireAdministrator.

I measured this on the host with offline builds in the scratchpad: i7-14700KF, RTX 4070 Ti SUPER, 21 interleaved warm runs per variant. Time to first frame:
- Win32 + Mica (Rust): 27 ms
- WinUI 3 C# Native AOT: 264 ms
- WinUI 3 C# JIT: 312 ms
- WPF .NET 10 Fluent: 397 ms
- WebView2 inside a WinUI host (stand-in for Tauri): web content at about 410–445 ms

Framework-dependent (bootstrapper) and self-contained Windows App SDK start equally fast. The bootstrapper costs under 1 ms warm, but it needs the runtime package installed, so self-contained is the better choice.

About 190 ms of the 264 ms WinUI floor is the first GPU device/compositor creation; on its own, D3D11CreateDevice takes 173–185 ms on hardware and 1.8 ms on WARP on this host. That cost is the same in every WinUI language, so C++/WinRT or Rust (Windows Reactor) could save only about 20–40 ms of managed startup. That gain is not worth the tooling cost. The old Rust attempt hand-closed the WinRT type graph through a 441-line filter and a 400-iteration cargo loop. Windows Reactor fixes that, but it is still a preview (the lib.rs entry is tagged "[not recommended]"). WinUI-specific startup tricks such as deferring the page or dropping the Fluent resources saved under 10 ms.

The out-of-process Rust engine is effectively free: about 4.5 ms from spawn to ready, and about 16 ms to return 541 uninstall entries (130 KB of JSON). Spawning it first thing in Main means the list data is ready before the window's first frame. Proposed budget for the dev host, warm: first frame under 300 ms at p50 (350 ms p90), program list with names under 350 ms, icons and sizes under 1 s, and cold launch after a reboot under 1 s. Verify the budget with in-app process-relative markers, an interleaved harness, WPR/WPA, and a launch step in the VM rig.

### Recommendations

- UI: C# .NET 10 + WinUI 3 on Windows App SDK 2.6.x (stable), unpackaged (WindowsPackageType=None, EnableMsixTooling=true), WindowsAppSDKSelfContained=true, PublishAot=true, x64+arm64. Reference only Microsoft.WindowsAppSDK.WinUI + .Runtime (62.6 MB instead of 143 MB). Stay on the CsWinRT 2.x TFM (net10.0-windows10.0.19041.0) until microsoft-ui-xaml #12625 is fixed.
- Engine: one Rust binary purge-engine.exe (static CRT) speaking newline-delimited JSON-RPC 2.0, with modes --stdio (unelevated, spawned first thing in Main), --broker (elevated via ShellExecuteEx runas, ACL-locked named pipe, client PID and image check, exits with the parent), --mcp (AI agent: read and propose only, execution needs a UI-minted approval token) and --cli (VM regression rig). Enforce the deny-list and backup-before-delete inside the engine.
- Change PARITY.md's 'always runs elevated via manifest' to asInvoker plus an on-demand elevated broker: requireAdministrator puts a UAC prompt in front of every launch and breaks drag and drop. Do not use a scheduled-task UAC bypass.
- Discard draft_clone/old-winui and the egui ui.rs entirely. Do not pursue Rust WinUI (Windows Reactor) until it reaches 1.0; the shared XAML/GPU floor caps its launch gain at about 40 ms.
- Adopt the startup budget, warm on the dev host: first frame ≤300 ms p50 / ≤350 ms p90, program names ≤350 ms, icons and sizes ≤1 s, cold after reboot ≤1 s. Gate CI with an interleaved harness (port scratchpad bench/run2.ps1) and in-app process-relative markers. Add a launch-timing step to the VirtualBox rig for cold starts.
- XAML rules: x:Bind only (no {Binding} under AOT), System.Text.Json source generators, a hand-rolled JSON-RPC client (no StreamJsonRpc), virtualized ListView/ItemsView with fixed-height rows and x:Phase, lazy pages as UserControls (not x:Load under Window), no WebView2/DataGrid/Win2D on the start path. Try the 2.3.1 XamlChangeIds (DefaultStyleOptimizations, OptimizeApplyStyles) and keep them only if measured.

### Open questions

- True cold-start (after reboot) numbers were not measured. They should come from the VM rig. The VM probably uses a software (WARP-like) render path, so its WinUI floor will differ from the host, where first D3D11 hardware device creation costs about 175 ms.
- How much of the ~175 ms GPU device cost is the NVIDIA driver and how much is the two virtual display adapters (SudoMaker, Virtual Desktop) enumerated by DXGI? Measuring on a typical iGPU laptop would set a realistic budget for other machines.
- Do the WinAppSDK 2.3.1+ opt-in XAML optimizations (DefaultStyleOptimizations, OptimizeApplyStyles) measurably reduce the 264 ms? Not tested yet.
- Should the program list use ListView with hand-made column headers, ItemsView, or the third-party WinUI.TableView (which documents AOT compatibility)? The built-in TableView is experimental-only in WinAppSDK 2.x.
- Distribution: plain xcopy/zip versus a small installer into Program Files. Program Files makes the broker's image-path check meaningful and avoids a user-writable elevated binary.
- PARITY.md currently states the app always runs elevated via its manifest. The user needs to confirm the switch to asInvoker plus an on-demand elevated broker.

## clone-reuse

The clone's non-UI code (about 1,485 lines in six modules plus about 150 lines of logic inside the 2,579-line ui.rs) builds without its UI. The VM harness at purge\vm\harness already compiles it headless through #[path]. Little of it should go into a Purge engine crate: about 6% as-is and about 25% after adaptation. The rest should be dropped. The part worth keeping is the uninstall-registry reader (programs.rs read_entry/load_all, about 46 ms for 521 entries on this host). Also worth keeping: a few util helpers (expand_env, filetime conversion, company_name/VerQueryValue), the top-most-new-item diff in trace::compare, and the installer-helper process names in wait_for_helpers. The leftover scanner (leftovers.rs) should be dropped completely; it is both unsafe and weak. I ran it read-only over every installed app on this host. It pre-ticks shared items owned by more than one product: both Python 3.12 and 3.13 claim %APPDATA%\Python, HKCU\Software\Python and HKLM\SOFTWARE\WOW6432Node\Python, and '.NET 8 Windows Server Hosting' claims C:\Program Files (x86)\Microsoft.NET. This comes on top of the known Notepad.lnk false positive. Its protected() check does not block roots such as C:\Program Files, and delete() calls remove_dir_all with no backup, no delete-on-reboot and no check that a folder is still used by another app. Store and startup enumeration go through PowerShell (1.57 s and 1.65 s measured here, and schtasks success is detected by matching the English word 'SUCCESS'). They should be rewritten on PackageManager, ITaskService and IShellLinkW, with StartupApproved for enable/disable state. Several rules in MECHANICS.md are UT-specific choices rather than Windows conventions: the duplicate rule, the install-time formula, the 0xC0000000 size mask, the merge rule for Windows Installer entries, the batch limit of 10, delete-value-and-remember startup disable, and the 'since last run' recent rule. They must not be carried over as 'UT behaviour'. ## competitors

No uninstaller surveyed (Revo Pro 5.5.4, IObit 14/15, Geek, HiBit, Total Uninstall, Ashampoo 16, Wise, BCU 6.3, Uninstall Tool, Uninstalr 3.2, winget, O&O AppBuster, PatchMyPC, MS PC Manager) knows which leftovers belong to an app. They all guess, in one of three ways: (a) record the install (Revo's revoflt.sys minifilter, UT Install Tracker, Total Uninstall/HiBit/Ashampoo snapshots), (b) use a vendor-curated, server-hosted per-app database (Revo Logs DB, Ashampoo "hundreds of profiles", IObit "3000+ stubborn programs"; all proprietary), or (c) match names (everyone; BCU adds a numeric confidence score). Microsoft withdrew its own MSI CleanUp utility because it damaged other components, and it does not support registry cleaners at all. Each of these becomes a hard safety rule below. The best ideas to combine are Total Uninstall's cross-program exclusivity check, BCU's additive confidence model and deny-lists, Revo/UT tracing, Wise/Uninstalr noticing uninstalls done outside the tool, Uninstalr's "no aggressive mode" stance, and O&O's dependency-aware Store removal. Name matching then becomes the weakest evidence instead of the only one. That would also explain the classes no tool removes today (VS Code's 135 OpenWithProgids keys come from Inno `uninsdeletevalue` without `uninsdeletekeyifempty`; Firefox's leftovers sit under the vendor name Mozilla). The only licence-clean seed data for a knowledge base is winget-pkgs (MIT), Scoop Main (Unlicense), Chocolatey community packages (Apache-2.0), BCU's deny-lists (Apache-2.0) and our own VM traces. ## ai-agent

Design: the agent is an untrusted advisor that can point at things; only the engine can prove them, and only the user can approve a deletion. The deterministic engine produces every candidate with structured evidence: BCU's additive ConfidenceRecords (Apache-2.0, ported with attribution), extended with evidence tiers and with "pre-uninstall reference" evidence that is captured before the vendor uninstaller runs. The agent gets four powers, all through one engine API shared by the WinUI app, a JSON CLI and an MCP stdio server: (a) re-rank and explain candidates (zero scoring weight); (b) propose probes such as "%APPDATA%\Mozilla is Firefox's vendor folder", which the engine checks with its own collectors (an agent-origin item is never preselected without Tier-A proof); (c) propose declarative per-app signatures for a local knowledge base, which must pass a lint check, a match against the ~348k-key pre-install baseline corpus we already have (snap-*-0.json) and a VM eval before the user can activate them; (d) review a dry-run plan, where it can only flag or untick items. Safety is enforced by construction, not by prompts. The MCP server is a separate unelevated binary with no executor code linked in. Every write goes through one Guard + Backup + Journal executor that refuses hard-denied locations whoever asked. Execution needs an interactive click in the elevated Purge window, bound to the plan's hash; UIPI and the UAC secure desktop stop lower-integrity agents from clicking or elevating. Everything is quarantined (same-volume move, plus a registry export) so it can be undone. Target MCP 2026-07-28: it is stateless with explicit handles, which fits scan_id/plan_id directly. The official C# SDK 2.x and Rust rmcp 3.x both implement it, and tool annotations are hints only, so safety must not depend on them. The VM rig becomes the regression gate: recall and precision are reported, while danger (any flagged item present in snap0), adversarial-agent escapes and prompt-injection canary success must all be 0. The rig needs three fixes first: a VM snapshot restore per app, real post-install footprint capture, and value-level plus last-write-time snapshots.

## safety-undo

Purge should never delete anything outright. Every removal becomes a reversible operation, written to a crash-safe journal (a log written before each step) and run by an elevated Rust engine process. Files and folders are moved (renamed) through an open handle into an admin-only quarantine folder on the same volume. That move is O(1), keeps ACLs, timestamps, alternate data streams (ADS), hard links and reparse points, and does not follow junctions. Registry items are backed up first into Purge's own lossless JSON: raw type number, raw bytes, the key's security descriptor (SDDL), its class, and whether it is a link. Not reg.exe/.reg text: lossy, no ACLs, one process per key. Not RegSaveKeyEx: it needs SeBackupPrivilege, does not support HKCR, and RegRestoreKey overwrites the whole subtree and fails if any handle is open. A .reg export can be generated from the JSON for people to read. Before anything runs, every item passes hard gates the AI agent cannot override: canonical-path and reparse checks (GetFinalPathNameByHandle and a FileId match), a deny-list, TrustedInstaller owner means deny, no write-access escalation (never take ownership, never use SeRestore to delete), files with hard links outside the plan are denied, cloud sync roots and placeholders are denied (moving or deleting them deletes from OneDrive and can trigger downloads), the item must not have existed before the app was installed, and shared files (SharedDLLs, MSI cache) are denied. Locked files go through retry with backoff, then Restart Manager (files only; RmGetList returns ERROR_ACCESS_DENIED for directories), then an offer to close the app or restart Explorer, then a boot-time move into quarantine with MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT), reconciled at the next launch. A System Restore point is optional, created early and in parallel. SRSetRestorePoint silently returns an old sequence number inside its 24h throttle, and Purge must never change SystemRestorePointCreationFrequency the way BCU does (Functions/Tools/SystemRestore.cs:44 sets it to 3 minutes). Restore points last 60 days on 24H2 and later and exclude user files, so they add to the quarantine and never replace it. TxF/KTM are out. Crash safety comes from an append-only JSONL journal with an intent record flushed before each operation, plus state probing on recovery (a rename leaves exactly one of source or destination). Undo replays inverse operations in reverse order, through the same validation gates and its own journal. The new benchmark property is round-trip fidelity in the VM rig: clean, undo, then a deep snapshot must equal the pre-clean one. Neither BCU's nor the clone's deletion code is worth reusing. BCU's file "backup" is a no-op that relies on the Recycle Bin, it backs up only string registry values, and it shells out to regedit /e per key. The clone deletes with remove_dir_all and keeps no backup.

### Recommendations

- Put all deletion in an elevated Rust engine (raw windows-sys APIs, not the winreg crate) with an admin-only named pipe. The WinUI 3 UI only plans, previews and approves.
- Replace 'delete' with 'quarantine': a handle-based, same-volume rename into an admin-only C:\ProgramData\Purge\Quarantine (or X:\.purge-q). Open with FILE_FLAG_OPEN_REPARSE_POINT, check GetFinalPathNameByHandleW and the FileId against the scan, then SetFileInformationByHandle(FileRenameInfo). Items that cannot be quarantined on their own volume start unchecked.
- Make Purge's own lossless JSON (raw type DWORD, raw bytes, SDDL, class, link flag) the canonical registry backup, flushed to disk before each delete. Offer a .reg export generated from it. Do not port BCU's regedit /e or its string-only value backup.
- Always address registry items as (real hive, explicit WOW64 view, path). Never write through HKCR or HKCU. Use HKU\<interactive user SID> passed in by the unelevated UI, to avoid the over-the-shoulder elevation profile mix-up.
- Run the hard validation gates twice (at plan time and right before execute): canonical path/FileId, deny-list, TrustedInstaller owner, other apps' paths and SharedDLLs, existed before install, hard links outside the plan, cloud sync root/placeholder, Microsoft-signed outside the app folder, registry link keys. The AI agent can add evidence but never touch gates.
- Never raise Purge's own access: no take-ownership, no ACL edits, no SeBackup/SeRestore privileges for deletes. Access denied becomes a reported deny.
- Locked files: backoff retry, then Restart Manager (register files only, since directories return ERROR_ACCESS_DENIED), then close app / stop service / restart Explorer with consent, then MoveFileEx DELAY_UNTIL_REBOOT moving *into quarantine* so the item stays undoable. Reconcile pending operations at the next launch.
- Implement a JSONL write-ahead journal (intent+flush, act, done) with state probing on recovery, and Resume/Roll back. Do not use TxF/KTM.
- Treat a missing target as success ('vanished'), collapse nested plan items, and never abort a batch on one error (fixes the BCU-console crash class).
- Restore point: off by default, auto for high-risk sessions. Create it in the engine process (CoInitializeSecurity) in parallel with prep. Detect the 24h throttle by comparing sequence numbers. Never change SystemRestorePointCreationFrequency.
- Undo = journaled inverse ops in reverse order, only to the original recorded path, with deny-list re-validation and skip-on-conflict. Keep registry/service/task backups 180 days and file quarantine 30 days; purge expired items in the background after the first frame.
- Mark AppX/sparse package removal (VS Code), services with stored task passwords, and boot-time deletes as reversibility partial/none, never pre-ticked.

# Plan reviews (draft v1)


### Review (safety): Not safe to build as written. The evidence model is sound. The main gaps are in where Tier A evidence comes from, the trust boundaries, and irreversible paths. Seven issues are critical. (1) Data dirs found by references become app roots, so `InsideAppRoot` (weight 9, Safe) can quarantine a user's whole library or recordings folder. (2) "Validated root" is never defined. Roots can be inferred from DisplayIcon or the uninstaller path, or taken from a user-writable HKU ARP entry. A System32 or Common Files root also defeats the L11 Defender protection. (3) Evidence found on a registry value can promote the containing key (OpenWithList, MuiCache, Run) to a delete target. The registry deny-list also misses User Shell Folders, Session Manager, Winlogon and ProfileList, and the plan drops BCU's skip of `SOFTWARE\Microsoft`. (4) The approval model's UIPI claim is false: the UI runs asInvoker, so any medium-IL process (including an MCP host with a shell) can click Approve or read the HMAC secret. `exec --confirm` also works for any already-elevated agent. (5) A leftover scan can run after an uninstaller that only modified, repaired or cancelled, or on a stale duplicate ARP entry, and then quarantine a live install. (6) Quarantine expiry is a silent permanent delete with no approval and no rule against following reparse points. (7) Boot-time MoveFileEx on user-writable paths lets SYSTEM follow a planted junction. Several of the plan's own rules are also wrong as written. The MSI rule '>1 client' does not catch the Python Launcher case. The +2 AI cap can lift a Tier A item into Safe. The IDF filter can leave zero tokens, which matches everything. `INetFwRules::Remove(name)` removes by a name that is not unique. Firefox's three Interface keys (the ISimpleDOM IIDs, which Thunderbird and other Gecko apps also register) are slated for preselection. The fixes follow.
- [critical] (5.2 Fingerprint roots / 5.3 InsideAppRoot) The fingerprint's roots include 'data dirs found by references'. Any directory named in an app's registry or config (Zotero DataDir, Calibre library_path, OBS recording path D:\Recordings, Arduino sketchbook, Steam library D:\SteamLibrary, a game's SavePath) therefore becomes a root. Everything under it then gets InsideAppRoot (Tier A, weight 9), reaches Safe and is preselected for whole-directory quarantine. The deny-list only blocks Known Folders and their ancestors, not their descendants or other folders on other drives.
  FIX: Keep two root types. An InstallRoot comes from the ARP InstallLocation, MSI or the installer manifest, and only it can produce InsideAppRoot. A ReferencedDataDir gets at most `ReferencedByApp` (Tier B), always has category UserData, and is never preselected. Add a hard rule: a directory referenced as a data, library, output, download or save path is never a whole-directory target. Add trap fixtures for each case (an app storing its library in Documents\X or D:\X).
- [critical] (5.2 / 4.1 / 5.10 root validation) 'Validated root' is never defined. Roots are inferred from DisplayIcon or the uninstaller path when InstallLocation is empty, and come from HKU Uninstall keys that any medium-IL process can write. A root can end up in C:\Windows\System32 (driver or OEM ARP entries), C:\Windows\Installer\{PC}, Common Files\<Vendor>, InstallShield Installation Information, a multi-product Vendor folder, or a folder under Downloads or Documents. With a System32 root, the MicrosoftSignedOutsideApp blocker never fires, because it only applies 'outside the app dir'. Every CLSID, service and task pointing into System32 then gets PointsIntoAppRoot (Tier A).
  FIX: Specify `validate_root()`. Reject any root that is inside or equal to a deny-listed path, is a Known Folder or a descendant of a user-content Known Folder (Documents, Desktop, Downloads, Pictures, Videos, Music), sits under a sync root, or is the parent of any other app's anchor (UninstallString, DisplayIcon, exe). A root inferred from DisplayIcon or the uninstaller path is Tier B and can never be quarantined whole. Evidence from user-writable sources (HKU ARP, %LOCALAPPDATA% stores) may never attribute machine-scope targets (HKLM, Program Files, services, tasks, firewall). Check MicrosoftSignedOutsideApp against %WINDIR% and Microsoft signatures regardless of the root.
- [critical] (5.3 / 5.6 REG-* / 5.10 registry deny) The plan never says whether value-level evidence (PointsIntoAppRoot, DanglingRef, InPreUninstallRefSnapshot) attaches to the value or to its containing key. Only InstallerManifest value records are split (8 on the value, 3 on the key). Suppose an OpenWithList, MuiCache, AppCompat Layers, UserAssist Count, Run, StartupApproved, SharedDLLs, Environment or FirewallRules key holds one value pointing at the app. It then reaches Safe as a key, and RegDeleteTreeW wipes every other app's entries. The structural deny-list does not list any of these containers. It also omits User Shell Folders and Shell Folders, Session Manager (KnownDLLs, PendingFileRenameOperations), Winlogon, ProfileList, IFEO, Fonts, Cryptography, Policies under HKU and under CurrentVersion, Explorer subtree roots and RegisteredApplications. - [critical] (7.8 retention / S4 Empty quarantine) Quarantine expiry runs 'after first paint at idle priority' and permanently deletes data (including user-data items such as profiles) with no approval. - [critical] (7.6 locked files) `MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT)` is used for candidates in user-writable locations (%APPDATA%, %LOCALAPPDATA%, ProgramData vendor folders that grant Users:Modify).   FIX: Use pending renames only for paths whose every ancestor is writable by administrators only. - [major] (5.7.1 associations / CLS-PROGID / 11.2 baseline fallback) P includes ProgIDs whose DefaultIcon points into the roots. - [major] (5.10 G1 / 7.5 execute / 10.2 traps) FILE_FLAG_OPEN_REPARSE_POINT only covers the last path component. - [major] (7.4 backup / 7.8 undo / 7.5 quarantine dirs) `C:\ProgramData\Purge` and `X:\.purge-q` are created on demand. By default, Users can create folders under ProgramData and at the root of non-system NTFS volumes. A standard-user process can therefore pre-create them (or plant a junction) with its own ACL and then read or tamper with regbackup JSON and service or task definitions. Undo then writes attacker-chosen HKLM values or creates services (CreateServiceW with the backed-up ImagePath) as admin. That is both a privilege-escalation path and a way to cause damage.
  FIX: Have the installer create ProgramData\Purge with a protected DACL. On every use, the broker opens each quarantine or session directory with OPEN_REPARSE_POINT and verifies: not a reparse point, owner is Administrators or SYSTEM, protected DACL. A service undo refuses an ImagePath outside the original root.
- [major] (4.4 uninstall runner) The broker runs UninstallString or QuietUninstallString at high IL for every entry, including HKU per-user entries and machine entries whose uninstaller sits in a user-writable directory. Any medium process can rewrite those values, so Purge becomes an elevation vehicle for arbitrary commands.

  FIX: Give each action type a typed inverse: re-insert the segment at its recorded index, restore the old default only if the current value equals what Purge wrote, and so on. For keys, restore all-or-nothing per subtree; any existing key under Installer\*, services or COM counts as a conflict and is skipped and reported. Add a fidelity test for each action type.
